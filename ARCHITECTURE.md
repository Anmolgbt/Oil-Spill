# ARCHITECTURE.md — OILTRACE AI

## Design goals (hackathon constraints)

1. **Zero mandatory external dependency.** No API key, no live satellite
   feed, no live AIS feed is required for the app to run and demo
   convincingly. Everything works from bundled synthetic data.
2. **Explainability over sophistication.** Every score the system produces
   traces back to a small number of named, weighted factors a judge can
   inspect in ~10 seconds.
3. **Same interface, swappable engine.** Every ML/physics piece (spill
   detection, drift model, attribution) is a plain function with a fixed
   signature. Replacing the demo body with a trained model or a live feed
   touches one file, not the UI.

## High-level data flow

The pipeline is **spill-first**, following the problem statement end to end:
imagery is what raises the alarm, drift physics turns "where it is" into "where
it came from", and AIS is queried only for that reconstructed place and time.
Behavioural anomaly detection runs late, on the handful of vessels that survive
the spatio-temporal filter — it narrows suspects, it does not find spills.

```
1. NEW SATELLITE SNAPSHOT ARRIVES
              ↓
2. AI CHECKS IMAGES FOR OIL
              ↓
        oil detected?
        /          \
      NO            YES
      ↓              ↓
   continue      SPILL FOUND
 monitoring          ↓
              3. CHARACTERISE
                 THE SPILL
                     ↓
              area / location
                     ↓
              4. HINDCAST
                     ↓
          Where was this oil
          likely located earlier?
                     ↓
          probable origin location
          + probable origin time
                     ↓
              5. CHECK AIS
                     ↓
       Which ships were near that
       place at that earlier time?
                     ↓
             filter ships
                     ↓
           6. SCORE SHIPS
                     ↓
       proximity + trajectory
       + behavioural anomaly
                     ↓
             ranked suspects
                     ↓
             7. FORECAST
                     ↓
       Where will the oil go next?
                     ↓
                DASHBOARD
```

Orchestrated by `services/pipeline.py:run_investigation()`, exposed as
`POST /simulate`. The run stops at step 2 with `status: CLEAR` when no oil is
found, so a quiet pass costs one model sweep and nothing else.

### Step map

| # | Step | Implementation | Model seam |
|---|---|---|---|
| 1 | Newest pass | `simulation_service.get_latest_snapshot()` | — |
| 2 | Oil detection | `spill_detection.scan_snapshot()` → `detect_oil()` per ship | `ml/spill_model.py` |
| 3 | Characterise | `spill_detection.characterize()` — area = mask pixels × ground area per pixel | uses the model's mask |
| 4 | Hindcast | `drift_model.estimate_origin()` — reverse drift vector + particle spread | — |
| 5 | AIS filter | `ais_service.find_vessels_near()` — closest approach inside the release window, gap detection | — |
| 6 | Anomaly + score | `vessel_attribution.score_anomaly()` → `factors_from_ais()` → `score_from_factors()` | `ml/anomaly_model.py` |
| 7 | Forecast | `drift_model.forecast_from_spill()` — forward envelopes at 6/12/24/36/48h | — |

Both models are absent while they are trained separately. With `DEMO_MODE=1`
their outputs come from `data/demo/pipeline_demo.json`; with `DEMO_MODE=0` the
adapters raise `NotImplementedError`. Everything between them — drift, the AIS
filter, the scoring — is genuinely computed in both modes.

### Data the pipeline reads

| File | Role |
|---|---|
| `data/simulation/snapshots/tN/shipN.jpg` | satellite passes; input to step 2 |
| `data/simulation/ships.json` | vessel identity and current position |
| `data/simulation/ais_history.json` | position over time; input to step 5. Generated by `scripts/generate_ais_history.py`, anchored to the origin the hindcast actually computes |
| `data/demo/pipeline_demo.json` | stands in for both models, plus drift parameters and thresholds |

### Worked demo run (`POST /simulate`)

```
t2 scanned      ship1 CLEAR · ship2 CLEAR · ship3 CLEAR · ship4 CLEAR
                ship5 OIL SIGNATURE DETECTED (0.91)
characterised   8.4 km² at 20.94 N, 72.29 E   (21000 mask px × 0.0004 km²)
hindcast        origin 21.045 N, 72.322 E · release 10:00–11:00 UTC
AIS             5 searched → 2 eliminated (37.0 km, 23.6 km) → 3 retained
ranked          #1 ship4  87   #2 ship2  77   #3 ship5  60
forecast        6 / 12 / 24 / 36 / 48 h envelopes
```

Note that the slick is observed near **ship5** but attributed to **ship4**: over
4.5 hours the oil drifted ~12 km from where it was released. That gap between
observed and release position is the whole reason step 4 exists.

### Legacy demo path

The original single-incident endpoints (`/detect-spill`, `/hindcast`,
`/forecast`, `/ais/*`, `/attribute`, `/report`) still run off the frozen
`data/demo/` fixtures and still back the existing dashboard:

```
backend/data/demo/*.json → data_store.py → services → routes/*.py
        → frontend/src/lib/api.ts (1.5s timeout, falls back to
          public/demo-data/*.json) → App.tsx
```

## Backend

FastAPI, organized by responsibility (per the brief's suggested layout):

| Module | Responsibility |
|---|---|
| `services/data_store.py` | Single seam between "demo JSON" and "real feed." Cached loaders only — no other module touches the filesystem. |
| `services/spill_detection.py` | `scan_snapshot()` runs the oil model across a pass; `characterize()` turns a mask into area. `detect_spill()` backs the legacy single-scene route. |
| `services/lookalike_filter.py` | Oil vs. biofilm / low-wind / other-dark-feature classification, so "dark patch" is never silently assumed to be oil. |
| `services/drift_model.py` | `estimate_origin()` traces a slick back along the drift vector to a probable release point, time window and particle spread; `forecast_from_spill()` projects it forward. Both are computed. The legacy `run_hindcast()` / `run_forecast()` replay prerecorded fixtures. |
| `services/ais_service.py` | `find_vessels_near()` reconstructs traffic around the **computed origin + release window** (not the visible slick), measures closest approach, detects AIS gaps, and drops vessels outside the search radius. |
| `services/vessel_attribution.py` | Factor calculation and weighted scoring, kept separate. `factors_from_ais()` derives the seven factors from track geometry; `score_from_factors()` applies the weights; `rank_ships()` ranks the survivors. `score_anomaly()` is the anomaly-model seam. |
| `services/report_service.py` | Assembles the consolidated Investigation Report payload from every other service. |
| `services/pipeline.py` | Orchestrates steps 1-7 and is the only module that knows their order. |
| `services/geo.py` | Haversine distance, bearings, destination points, timestamp parsing. |
| `services/simulation_service.py` | Snapshot discovery and per-ship image resolution. |

### Attribution weights

```
Time Match              20%
Source Region Overlap   25%
Trajectory Similarity   20%
Distance                15%   (derived: max(0, 100 − km × 10))
Behaviour Anomaly       10%
AIS Suspicion            5%   (pipeline: 100 − continuity; a dark interval
                              overlapping the release window scores high)
Vessel Relevance         5%
```

This is intentionally simple and auditable — a judge can multiply the
numbers on screen and get the shown score. It is explicitly **not**
presented as scientifically validated (see README → Scientific Honesty).

### Endpoints

| Method | Path | Purpose |
|---|---|---|
| POST | `/detect-spill` | Run (demo) spill detection + look-alike filter |
| POST | `/characterize-spill` | Spill metrics + source reconstruction |
| POST | `/hindcast` | Backward particle simulation |
| POST | `/forecast` | Forward particle/polygon simulation |
| POST | `/ais/candidates` | AIS vessels found in source region + release window |
| POST | `/attribute` | Full explainable score breakdown for one vessel |
| POST | `/simulate` | **Run the full spill-first pipeline over one satellite pass** |
| GET | `/snapshots` | Available satellite passes |
| GET | `/incident/{id}` | Full incident object |
| GET | `/report/{id}` | Consolidated investigation report |

All endpoints read the bundled demo fixtures under `backend/data/demo/` whenever
`DEMO_MODE=1` (the default). With `DEMO_MODE=0` the services raise
`NotImplementedError` until the real implementations are connected. See
`backend/data/demo/README.md` and `backend/core/config.py`.

## Frontend

- **`lib/api.ts`** — every fetch function tries the FastAPI backend with a
  1.5s timeout, then falls back to the identical JSON bundled under
  `public/demo-data/`. The UI never shows an error state because of this —
  it always has *some* valid response to render.
- **`App.tsx`** — one component holding the whole dashboard: the investigation
  state machine, all Leaflet map layers (spill polygon, source region, hindcast
  particles, forecast envelope, vessel tracks/markers), the KPI cards, the
  evidence panel, and the replay/report modals. Every displayed investigation
  value reads from API state; none are literals.
- **`styles.css`** — plain CSS, one file, dark maritime theme. No Tailwind.

## Why these simplifications were made

| Cut corner | Why it's OK for an MVP demo |
|---|---|
| No trained segmentation model | A real Sentinel-1 U-Net would take days to train/validate; the interface is identical, so swapping it in later is a one-file change. |
| No live AIS/Sentinel/metocean feeds | Judges need the demo to work with no network flakiness; `data_store.py` is the explicit seam for later integration. |
| No heatmap plugin, no vector-field grid | Two polygons + a handful of arrow markers read correctly on a projector at demo distance, at zero extra dependency cost. |
| Deterministic instead of "real" ML scoring | Explainability was an explicit judging criterion — a formula a judge can verify by hand is more convincing than a black-box confidence number. |
